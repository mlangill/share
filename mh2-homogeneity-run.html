Running MH2 on Homogeneity with Claude Code

I asked Claude Code to work through the Microbiome Helper 2 marker-gene SOP with me, one step at a time, on the IMMSA Homogeneity data (V4, 515F/806R, MiSeq 2×300). This page shows the prompts I typed, what the work looked like, what it caught, where it got things wrong, and what it would cost through the API.

Ground rules

How we worked

Claude Code runs in the terminal on kronos. It reads files, runs shell commands and edits files itself, and I approve or redirect as it goes. I set the rules in my first few prompts.

PROMPTMy research lab processes 16S data using Microbiome Helper (which we develop). The SOP for 16S data is here: […] I want to work through that SOP for some of the data here (maybe Homegeneity)? I would prefer if we work through it together where you tell me what files to look at (and you give me your suggestion) before moving to the next step. Does that sound good? Anything to discuss before we start?
PROMPT, sent while a job was runningthis is a shared server so can you check to make sure you don't overload the server when running?
PROMPTYou can unzip and look at the numbers yourself, but I will copy them locally and view within browser. Lets use 12 threads (instead of 8). […] Also, I am going to want to show this workflow off to my lab, so can you keep track of things …

What Claude did with that

  • Ran every heavy step with nice -n 19 and 12 threads, and checked free memory first.
  • Stopped after each step, told me which .qzv files to open, and gave its own reading of the numbers before asking to continue.
  • Kept a running WORKFLOW_LOG.md with every command and decision, plus PRESENTATION_NOTES.md, which this page was built from.
  • Saved “memory” notes, so a new session knows the project, the 12-thread rule and the log location.

Claude Code features that came up

  • Auto mode: commands run without a prompt, but risky ones still get flagged. One rm -rf was flagged (Step 8).
  • Background tasks: long jobs (Deblur, SEPP) run detached, and Claude is notified when they finish.
  • Monitors: a 30-second memory watch during SEPP is what exposed the thread overrun.
  • ! prefix: ! ls runs a command myself, inside the session.
  • Compaction: the conversation filled the context window once and was summarized automatically, with no lost work.
The headline result

Where the reads went

Read counts after each stage, summed over all samples, for this run and for the original DADA2 analysis that came with the data. Most of the gain came from two fixes Claude proposed: matching N calls in the primer as wildcards, and letting vsearch merge staggered pairs from read-through.

Most of the extra merged reads didn't survive denoising: the final count is +8%, not +53%. Claude's hypothesis, which we haven't tested, is that the extra pairs rescued with maxdiffs 20 are noisier, so Deblur throws more of them out. After the SOP filters, the final table has 660 ASVs and 11.53 M reads across 89 samples.

  • A
    Explained the 34 bp median. Most reads in the negatives are 35-N placeholder reads, which the MiSeq writes when on-instrument adapter trimming leaves less than 35 bp (adapter or primer dimers). O22 is 80% placeholders and V22 is 87%.

Primer trimming
19.94 M pairs kept
original: 11.60 M
$ nice -n 19 qiime cutadapt trim-paired --p-cores 12 \
    --p-front-f GTGYCAGCMGCCGCGGTAA --p-front-r GGACTACNVGGGTWTCTAAT \
    --p-adapter-f ATTAGAWACCCBNGTAGTCC --p-adapter-r TTACCGCGGCKGCTGRCAC \
    --p-match-read-wildcards --p-times 2 --p-discard-untrimmed --p-no-indels ...
Pairs kept: 97.3% (median per sample)   original analysis: 56.4%
  • A
    Root-caused the original 46% loss. cutadapt counts an N in a read as a mismatch. Up to 4 Ns in the 20-nt primer meant the primer wasn't found, the read stayed untrimmed, and then --max-n=0 discarded it. One flag, --match-read-wildcards, recovered 8.3 M pairs.
  • A
    Caught read-through, which the SOP doesn't handle. With 2×300 reads on a ~253 bp insert, about 70% of R1 reads run into the opposite primer. Claude added the reverse-complement primers as 3′ adapters, and predicted that vsearch would need allowmergestagger.
  • A
    Checked its own trimming by parsing all 95 cutadapt reports: at most 0.03% of kept pairs could still carry a 5′ primer.
PROMPTWhy do tmp on disk? Isn't it faster having it on RAM?
  • T
    Overstated the advice about /tmp. Claude had suggested moving QIIME 2's temp files from RAM-backed /tmp to disk. When I pushed back, it agreed: these steps are CPU-bound, and /home is on NFS, which would be slower. My judgment overruled the model here.

monitor › status: avail=121GB mine=0.5GB sepp_running=2

$ ps ... running pplacer 48   load average 40.8   (asked for --p-threads 12)
$ taskset -a -cp 36-47 <each SEPP pid>   pinned 106 processes → ~10 cores
  • A
    Caught a tool ignoring its thread limit, and fixed it live. The memory watch showed 105 processes, so Claude looked closer. Without killing the job, it pinned every process to 12 cores. SEPP finished in 28 min.
PROMPTany idea why pplacer used so many threads? Has that bug (or behaviour) been seen elsewhere?
  • A
    Traced it to a single commit. In SEPP 4.5.6, -x is stored in scheduler.default_cpus but never read, so the job pool uses cpu_count(), which is 48 on kronos. Using the GitHub API, Claude found commit f501930 (2025-07-14, “remove unused variable default_cpus”), which deleted the line that used it. It found no existing issue. That took about 5 tool calls from symptom to commit.

Scorecard

Strengths and weaknesses

Where it was strong

  • Reading raw evidence (FastQC tables, cutadapt reports, source code) and connecting it to a cause.
  • Checking its own work: parsing every report, cross-checking against the original analysis.
  • Cheap tests before expensive runs: the 4-sample merge sweep, test-loading the classifier.
  • Fixing its environment without being asked (MultiQC), and staying out of system files.
  • Root-causing problems in tools, not just working around them (SEPP).

Where it slipped

  • Confident claims before checking: no controls, “mock community”, a classifier download that doesn't exist.
  • Knowledge that's out of date for fast-moving tools (QIIME 2 2026.4 changes).
  • Shell habits that need a safety net: an unguarded rm -rf, a guessed file name.
  • Too many threads before I set the rule. Rules for a shared server need to be stated up front.
  • Runtime estimates were poor (Deblur: 1–2 h predicted, 20 min actual).

The pattern: it's fast and thorough with evidence in front of it, and weakest when it relies on memory. Asking “how do you know?” and “why?” paid off every time.

For the MH2 maintainers

SOP updates this run turned up

These came out of one pass through the wiki on QIIME 2 2026.4. All are written up with commands in WORKFLOW_LOG.md.

Denoising summary
feature-table summarize changed. Use --o-summary plus the required --o-feature-frequencies and --o-sample-frequencies.
Taxonomy
The shared classifiers won't load in 2026.4 (they were built with scikit-learn 1.4.2, and 2026.4 has 1.7.1). QIIME 2 now points to SILVA (144, with a V4-515f-806r build) and GTDB on Zenodo. Greengenes2 would need training in-house.
SEPP
--p-threads is ignored in SEPP 4.5.6. Wrap the command: taskset -c 0-11 nice -n 19 qiime fragment-insertion sepp .... An upstream issue or PR could restore the two deleted lines.
Export
Add qiime tools export --input-path taxa/classification.qza --output-path taxa before the sed step.
Primer trimming
Consider --p-match-read-wildcards by default, and reverse-complement 3′ adapters for 2×300 V4 runs, where reads run through the opposite primer.
Read merging
With read-through, use --p-allowmergestagger, and test maxdiffs on a few samples first.

How to read it

  • Each request re-sends the whole conversation, but mostly from a cache at 5% of the normal price. That's why 21 M tokens read cost less than 0.5 M written.
  • Claude's own output is under 1% of the tokens but about a quarter of the cost.
  • The pipeline compute ran on kronos and costs nothing here. A 28-minute SEPP run is one cheap request plus a notification when it finishes.

Sonnet instead of Opus?

  • Sonnet 5.5 costs exactly half per token in every category, so the same session would be about $5.32, saving $5.31.
  • That assumes the same tokens. A different model may take more or fewer turns, and the judgment-heavy moments (the N-artifact diagnosis, tracing the SEPP bug) are where models differ most.
  • A reasonable split: Sonnet for routine steps, Opus when something doesn't add up.

“new task? /clear to save 124.5k tokens”

The terminal shows this because the conversation is about 124.5k tokens long, and every new request re-reads all of it. That's about $0.025 per request on Opus, or $0.012 on Sonnet. /clear starts fresh at almost zero. Because the log, the notes and the memory files are saved on disk, a new session can pick the project back up. /compact is the middle option: it summarizes the conversation and carries on.

Not counted

Web-page reads (WebFetch) use a separate small model, and the one automatic compaction probably isn't in the transcript totals, so the real figure is slightly higher. Building this page added more tokens after the totals were taken. On the Pro plan none of this is billed per token; it counts toward the plan's usage limits, which /usage shows.
